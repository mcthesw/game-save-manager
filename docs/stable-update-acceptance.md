# 正式版发布与应用更新验收

本 PR 实现完整发布、默认手动检查和同格式下载入口。Windows 的分阶段应用内安装在后续 PR 中实现；下列安装规则是已确认的验收目标，不代表本 PR 已启用安装。

## 产品规则

- 正式版由维护者在 `dev` 手动运行 **Publish Stable**，输入与 `Cargo.toml` 一致的 `X.Y.Z`。所有平台构建必须成功、发布附件齐全后才能公开；不允许缺少平台的正式版。
- Nightly 仍按日构建并公开预发行版。先完成所有构建，再替换附件；不进入应用的正式版更新入口。
- 默认只手动检查更新。用户可以在设置中主动开启启动检查；自动检查只提示，绝不自动下载、安装。
- 优先验收 Windows NSIS/MSI 的应用内安装。Linux/macOS 仍必须构建成功，首期提供手动下载，逐平台验收后再启用应用内安装。
- 点击“下载”只下载并验证安装包，用户仍可正常备份和同步。下载完成后显示“重启并安装”，由用户再次点击。
- 安装前停止接受新的业务操作，等待已经开始的操作（包括后台备份、恢复与同步）结束。“暂不重启”可以取消等待并恢复使用，不中止已经开始的写入。
- 首期下载包只保存在当前进程内；退出应用后再次更新需要重新下载，不建立持久化下载缓存。
- “稍后”暂缓当前版本的提示；用户手动检查仍可查看该版本。设置页不重复显示全局更新横幅。

## 首次发布

当前应用版本为 `1.9.1`，配置文件格式仍为 `1.9.0`。应用版本升级本身不触发配置迁移。

旧版没有应用更新器。首次正式版的发布说明和下载说明必须告知旧用户：需要手动安装一次新版本，之后才可使用应用内更新。1.9.0 测试包用户也使用这一入口。

发布前将变更合入 `dev`，完成旧安装到新安装的 Windows 升级验收，再手动运行 **Publish Stable**。版本不符、tag 已存在或版本不高于最新正式版时拒绝发布。合并 PR 不会发布正式版。

更新签名私钥由维护者管理，通过 `TAURI_SIGNING_PRIVATE_KEY` 提供给构建。发布前确认有独立安全备份；已安装客户端验证未来更新需要同一签名身份。不要将私钥写入仓库。

## 各安装形式

| 当前安装 | 更新入口 |
| --- | --- |
| Windows NSIS / MSI | 下载并验证同格式包，再由用户点击“重启并安装” |
| Windows 便携 ZIP | 打开同格式下载，用户手动更新 |
| Linux AppImage / DEB / RPM | 打开同格式下载，用户手动更新 |
| macOS DMG | 打开 DMG 下载，用户手动安装 |
| 无法识别的安装形式 | 打开正式版页面，用户选择适用包 |

应用提供更新内容链接；应用内下载或安装失败时保留手动下载入口。包管理器分发尚未纳入本轮。

## 验收边界

构建、签名文件存在、单元测试和浏览器验证不能证明安装升级成功。

| 范围 | 必须验证的行为 |
| --- | --- |
| 发布脚本 | 真实的 `nsis/`、`msi/`、`deb/` 等 artifact 子目录能选出完整附件；缺包或缺签名拒绝发布 |
| 默认值 | 新配置与缺少字段的旧配置均关闭启动检查；保留用户显式选择 |
| 更新流程 | 下载完成不安装；重复点击不会启动第二次操作；重载页面能恢复当前进程的进度 |
| 写入协调 | 已有写入全部结束后才安装；等待期间新写入被拒绝；取消等待或安装失败恢复业务入口 |
| Windows 安装 | NSIS/MSI 分别从真实旧安装升级；保持安装形式、安装位置和用户数据；权限与重启正常 |
| 首次公开正式版 | `releases/latest/download/latest.json` 返回公开版本及正确下载地址 |
| Nightly | 替换为同次构建的完整附件、删除旧附件、保持 prerelease，成功后才推进 `latest-built` |

真实 Windows 安装升级、正式发布和新的 Nightly 发布仍需实际运行验收，不能提前标记完成。Linux/macOS 首期只承诺手动下载。
